# Jarvis 66 — חבילת החלטה להפעלת moderation

סטטוס: `local-migration-validated; activation-blocked-on-owner-policy`

## ראיות מקומיות

- migration נבדקה על מסד SQLite סינתטי שנוצר מסכמת ה־community הקודמת.
- rollback בתוך transaction החזיר את הסכמה והנתונים למצב הקודם.
- תגובות קיימות נשמרו וקיבלו `community_unreviewed` ו־`visible` בלבד.
- מחיקת תגובה מוחקת ב־cascade תגובות־בת, likes, views, reports ואירועי audit שלה.
- מחיקת מדווח מוחקת את הדיווחים שלו, אך לא את התגובה שעליה דיווח.
- מחיקת אדמין נחסמת כל עוד הוא actor באירוע audit; לאחר מחיקת האירוע,
  `moderated_by` ו־`resolved_by` הופכים ל־NULL.
- נוסף ל־migration ה־foreign key שהיה חסר עבור `moderated_by`, כדי להתאים לסכמה חדשה.
- הרצה ישירה שנייה של migration נכשלת ב־`duplicate column`; יש להפעיל אותה פעם אחת
  דרך מנגנון migrations שעוקב אחר גרסאות, ולא כקובץ SQL ידני חוזר.

## סדר הפעלה בטוח מוצע

1. לאמת קיום `GOOGLE_CLIENT_ID` בלי לחשוף ערך.
2. לפרוס קוד כאשר שני feature flags כבויים.
3. לגבות את D1 ולאמת נקודת שחזור.
4. להפעיל migration פעם אחת דרך מנגנון migrations ולקרוא בחזרה schema ו־FK.
5. להפעיל תחילה את שער השרת ולבדוק guest/user/admin סינתטיים.
6. להפעיל את שער הלקוח רק לאחר שה־API וה־audit אומתו.

Rollback תפעולי מתחיל בכיבוי שער הלקוח ואז שער השרת. אם כבר נוצרו נתוני moderation,
מומלץ forward-fix או export לפני שינוי schema; rollback מוחק של טבלאות או עמודות אינו
בטוח כברירת מחדל. לפני שנוצרו נתוני moderation, ניתן לבצע rollback DDL מאושר לאחר גיבוי.

## חלופות מדיניות והשלכות

### A — מחיקה מלאה עם התוכן

reports ו־audit נמחקים כאשר תגובה או חשבון רלוונטי נמחקים. זו החלופה המצמצמת ביותר
מבחינת פרטיות ושמירת מידע, אך היא מחלישה חקירה בדיעבד והוכחת עקביות moderation.

### B — audit תפעולי ממוזער

שומרים אירוע, פעולה, סיבה וזמן ללא טקסט התגובה וללא זהות מדווח ישירה; קשרים לתגובה
או לחשבון נעשים nullable או pseudonymous בעת מחיקה. זו חלופת האיזון המומלצת לבדיקה:
היא שומרת עקיבות בסיסית בלי לשמר תוכן קהילתי שנמחק. היא דורשת migration נוסף והחלטת
retention מפורשת לפני הפעלה.

### C — audit ארוך־טווח ובלתי־מחיק

הראיה התפעולית נשמרת גם לאחר מחיקת תוכן או חשבון. זו חלופה חזקה לחקירה, אך בעלת נטל
הפרטיות, האבטחה והציות הגבוה ביותר; אין להפעילה ללא צורך מתועד ואישור מתאים.

## מודל אדמין

- `ADMIN_EMAIL` יחיד: פשוט, אך יוצר נקודת כשל והעברה תפעולית חלשה.
- טבלת תפקידים/allowlist מפורשת: מאפשרת מספר אדמינים, ביטול והרשאה מתועדת; מומלצת
  לשלב הנוכחי אם ימונה בעלים תפעולי.
- קבוצת IdP חיצונית: governance ארגוני חזק יותר, במחיר מורכבות ותלות נוספות.

לא נקבעו כאן תקופת retention, בעלים תפעולי או מדיניות מחיקה בשם המשתמש.

## השאלה הראשונה לבעלים

האם בעת מחיקת תגובה או חשבון יש למחוק גם את כל ראיית ה־moderation (חלופה A), או
לשמור audit תפעולי ממוזער ללא תוכן וללא זהות ישירה (חלופה B, ההמלצה לבדיקה)?

# Jarvis 66 — חבילת החלטה להפעלת moderation

סטטוס: `all-planning-decisions-approved; local-controls-validated; activation-gated`

## ראיות מקומיות

- migration נבדקה על מסד SQLite סינתטי שנוצר מסכמת ה־community הקודמת.
- rollback בתוך transaction החזיר את הסכמה והנתונים למצב הקודם.
- תגובות קיימות נשמרו וקיבלו `community_unreviewed` ו־`visible` בלבד.
- מחיקת תגובה מוחקת ב־cascade תגובות־בת, likes, views ו־reports, אך משמרת audit
  ממוזער ללא `comment_id` או `actor_id` עד לתפוגה.
- מחיקת מדווח מוחקת את הדיווחים שלו, אך לא את התגובה שעליה דיווח.
- מחיקת אדמין מאפסת את ההפניות התפעוליות ומשמרת audit ממוזער ללא קישורים ישירים.
- נוסף ל־migration ה־foreign key שהיה חסר עבור `moderated_by`, כדי להתאים לסכמה חדשה.
- הרצה ישירה שנייה של migration נכשלת ב־`duplicate column`; יש להפעיל אותה פעם אחת
  דרך מנגנון migrations שעוקב אחר גרסאות, ולא כקובץ SQL ידני חוזר.
- migration נוספת משמרת אירועי audit קיימים, מוסיפה `expires_at` של 90 יום ומחליפה
  את יחסי המחיקה ל־`SET NULL`; rollback טרנזקציוני ו־schema parity עברו מקומית.
- מחיקת תגובה או actor מתחילה חלון חדש של 90 יום לאירוע הממוזער.
- purge מפורש נבדק רק מול נתונים סינתטיים. הוא אינו מתוזמן ואינו רץ בפרודקשן.

## סדר הפעלה בטוח מוצע

1. לאמת קיום `GOOGLE_CLIENT_ID` בלי לחשוף ערך.
2. לפרוס קוד כאשר שני feature flags כבויים.
3. לגבות את D1 ולאמת נקודת שחזור.
4. להפעיל migration פעם אחת דרך מנגנון migrations ולקרוא בחזרה schema ו־FK.
5. להפעיל תחילה את שער השרת ולבדוק guest/user/admin סינתטיים.
6. להפעיל את שער הלקוח רק לאחר שה־API וה־audit אומתו.

Rollback תפעולי מתחיל בכיבוי שער הלקוח ואז שער השרת. אם כבר נוצרו נתוני moderation,
מומלץ forward-fix או export לפני שינוי schema; rollback מוחק של טבלאות או עמודות אינו
בטוח כברירת מחדל. לפני שנוצרו נתוני moderation, ניתן לבצע rollback DDL מאושר לאחר גיבוי.

## החלטות שהתקבלו

- audit תפעולי ממוזער נשמר לאחר מחיקת תגובה או חשבון, בלי תוכן ובלי זהות ישירה.
- תקופת השמירה היא 90 יום.
- Jarvis הוא אחראי המיון והמעקב המיועד; מקרים הדורשים החלטת בעלים או איש מקצוע
  מועברים לבעלים בצ׳אט הזה.
- אין בכך אישור קליני אוטומטי, הרשאת moderation חדשה או חיבור תפעולי מתמשך.

## retention לרשומות דיווח

- `pending`: נשמר עד הכרעה; אין למחוק אוטומטית דיווח שממתין לבדיקה.
- `dismissed` ו־`actioned`: מקבלים `expires_at` של 90 יום ממועד ההכרעה.
- מחיקת תגובה או מדווח עדיין מפעילה את יחסי ה־cascade הקיימים; אין שינוי תוכן.

## מחיקה אחרי 90 יום

`expires_at` הוא סימון זכאות בלבד. הבקר המקומי דורש preview פסאודונימי, גיבוי
AES-256-GCM של ה־batch ל־7 ימים ואישור שתואם ל־fingerprint. purge מוגבל ל־500
רשומות audit/report בהרצה והלוג הממוזער נשמר 90 יום. אין כרגע cron, webhook,
הרשאת D1 מתמשכת או הרצת purge בפרודקשן.

## התראות ו־triage

המימוש המקומי מסווג `potentially_unsafe`/`misleading` לבדיקת איש מקצוע או בעלים,
`harassment`/`other_policy` להחלטת בעלים, ו־`spam` לתור שגרתי. הוא מפיק מעטפת
התראה מצומצמת במצב `not_configured`, ללא שליחה חיצונית וללא פעולה אוטומטית.

## מודל אדמין

- `ADMIN_EMAIL` יחיד: פשוט, אך יוצר נקודת כשל והעברה תפעולית חלשה.
- טבלת תפקידים/allowlist מפורשת: מאפשרת מספר אדמינים, ביטול והרשאה מתועדת; מומלצת
  לשלב הנוכחי אם ימונה בעלים תפעולי.
- קבוצת IdP חיצונית: governance ארגוני חזק יותר, במחיר מורכבות ותלות נוספות.

ההכרעות הושלמו. נותרו רק שערי מימוש ופרסום: bootstrap בעלים, גישה מצומצמת,
migration/schema readback, smoke והרשאת הפעלה נקודתית. ראו runbook הייעודי.
